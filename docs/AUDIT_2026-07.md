## Podsumowanie (TL;DR)

Aplikacja jest w dobrym stanie inżynierskim: czytelny podział na hooki/serwisy,
sensowna obsługa offline, RLS oparte na `household_id`, sekrety OpenAI trzymane
po stronie serwera, brak `dangerouslySetInnerHTML`/`eval`. Testy jednostkowe i
integracyjne pokrywają logikę obliczeń, kolejkę offline i import CSV.

## 1. Bezpieczeństwo

### S1 (Wysoka) — Cross-tenant IDOR w `match_category_rules`
Plik: `migration/004_category_embeddings.sql:68-98`

```sql
create or replace function public.match_category_rules(
  query_embedding ..., match_threshold float, match_count int, p_household_id uuid)
returns table (...)
language sql stable security definer          -- omija RLS
set search_path = public, extensions
as $$
  select ... from public.category_rules cr
  where cr.household_id = p_household_id       -- household_id bierze się z argumentu
    and 1 - (cr.embedding <=> query_embedding) > match_threshold
  ...
$$;
grant execute on function public.match_category_rules to authenticated, anon;
```

Problem: funkcja działa jako `SECURITY DEFINER` (pomija RLS) i filtruje po
`p_household_id` **przekazanym przez klienta**, bez weryfikacji, że wołający
należy do tego gospodarstwa. Każdy zalogowany — a nawet niezalogowany (`grant …
to anon`, klucz anon jest publiczny w bundlu) — użytkownik znający cudzy
`household_id` może wykonać:

```js
supabase.rpc('match_category_rules', {
  query_embedding: <dowolny wektor>, match_threshold: -1,
  match_count: 1000, p_household_id: '<cudze-uuid>' })
```

i wyciągnąć `description` reguł kategorii (opisy transakcji = prywatne dane
finansowe) innego gospodarstwa. `household_id` to UUID (trudny do zgadnięcia),
więc to nie jest „otwarte drzwi", ale bezpieczeństwo nie powinno opierać się na
nieodgadywalności identyfikatora, a funkcja jest wystawiona także dla `anon`.

Rekomendacja (gotowa migracja: `migration/009_fix_match_rules_security.sql`):
- wymusić w treści funkcji `p_household_id IN (SELECT household_id FROM profiles
  WHERE id = auth.uid())`, albo zignorować argument i wyprowadzić household z
  `auth.uid()`;
- cofnąć `grant ... to anon`.

### S2 (Wysoka) — Zależność od „Confirm email" przy przejęciu gospodarstwa
Pliki: `migration/005_email_password_auth.sql:12-14`, `006`, `007_auto_create_household.sql:49-70`

Trigger `handle_new_user()` przy rejestracji dowiązuje nowego użytkownika do
`household_id` istniejącego profilu **o tym samym emailu** (migracja z ery
Google) i usuwa stary profil. Jeśli w Supabase Dashboard nie jest włączone
Authentication → Email → „Confirm email", ktokolwiek może zarejestrować konto na
cudzy (legacy) email i przejąć całe gospodarstwo wraz z historią transakcji.
Wymóg jest udokumentowany wyłącznie w komentarzu SQL — nie ma go w README ani w
kodzie, więc łatwo o pominięcie przy wdrożeniu.

Rekomendacja: udokumentować twardo w `docs/SETUP_*` i README jako krok
obowiązkowy; rozważyć dopasowanie legacy-profilu tylko dla `NEW.email_confirmed_at
IS NOT NULL`.

### S3 (Średnia) — Fallback `getUserProfile()` przypisuje do `households[0]`
Plik: `src/services/api.js:30-51`

Gdy profil nie istnieje (`PGRST116`), kod pobiera `households` z `.limit(1)` i
przypisuje użytkownika do **pierwszego napotkanego** gospodarstwa. Dziś ścieżka
jest w praktyce martwa (household tworzy trigger 007, a RLS `households_select_
member` zwróci pustą listę dla użytkownika bez profilu), ale to niebezpieczny
wzorzec: przy jakiejkolwiek regresji RLS nowy użytkownik trafiłby do cudzego
gospodarstwa. Zalecam usunięcie tej gałęzi — tworzenie profilu należy wyłącznie
do triggera po stronie serwera.

### S4 (Średnia) — Podatności zależności (`npm audit`)
9 podatności: **critical** `vitest` (odczyt/wykonanie pliku, tylko gdy działa
Vitest UI server), **high** `vite` (path traversal / arbitrary file read dev
servera), `ws`, `launch-editor`; 1 low. Wszystkie w `devDependencies` — nie
trafiają do produkcyjnego bundla, więc ryzyko realne głównie na maszynie
developera. Zalecane: `npm audit fix` (vitest, ws bez breakingów) oraz aktualizacja
vite do 6.4.3.

### Rzeczy zweryfikowane jako OK
- Brak `dangerouslySetInnerHTML`, `eval`, `new Function` — React escapuje treść;
  opisy/komentarze transakcji renderowane jako tekst.
- Klucz OpenAI trzymany serwerowo (`api/embeddings.js`), proxy wymaga ważnego
  tokenu Supabase, limituje liczbę i długość tekstów.
- `.gitignore` obejmuje `.env*`, wyciągi bankowe (`Zestawienie*`, `*.numbers`);
  w historii gita brak commitniętych sekretów (tylko pliki `.env.example`).
- RLS włączone na wszystkich tabelach domenowych; polityki oparte na
  `profiles.household_id`. Permisywna polityka `anon` na `category_rules`
  została już usunięta (migracja 008).
- Detekcja wygaśnięcia sesji (`isSessionError`) obsługuje brak `.status` w
  PostgREST (kod `PGRST301`), z auto-wylogowaniem i czyszczeniem `sessionStorage`.

## 2. Spójność danych i logika finansowa

### D1 (Średnia) — Nieinwalidowany cache roczny
Pliki: `src/services/api.js:539-571`, `src/hooks/useYearlyData.js`

`getTransakcjeForYear` cache'uje wynik w `sessionStorage` z TTL 30 min. Cache
jest czyszczony tylko przy wylogowaniu (`sessionStorage.clear()`), ale **nie** po
dodaniu/edycji/usunięciu transakcji ani po imporcie CSV. Scenariusz: użytkownik
otwiera widok „Rok" (cache set), wraca do „Miesiąc", dodaje/edytuje transakcję,
wraca do „Rok" — przez maks. 30 min widzi nieaktualne sumy roczne, wykresy YoY i
oszczędności skumulowane. Subskrypcje realtime odświeżają tylko dane miesięczne
(`fetchDataRef`), nie ruszają cache rocznego.

Rekomendacja: inwalidować `yearly_transakcje_*` przy każdej mutacji transakcji
(add/update/delete/batch import) — np. helper `invalidateYearCache(rok)` wołany w
`api.addTransakcja/updateTransakcja/deleteTransakcja/addTransakcjeBatch`.

### D2 (Niska) — Dryf zmiennoprzecinkowy w sumach
Pliki: `src/utils/calculations.js:56-82`, `src/App.jsx:1267-1269`

Kwoty w bazie to `numeric` (dobrze), ale `calculateIncome/calculateExpenses` i
`bilans` sumują floaty przez `reduce` bez zaokrąglenia. Przy wielu transakcjach z
groszami możliwy błąd rzędu 0,01 zł w wyświetlanej sumie (`aggregateByCategory` i
`aggregateByPerson` już zaokrąglają do 2 miejsc — warto ujednolicić). To kwestia
prezentacji, nie zapisu danych.

Rekomendacja: zaokrąglać sumy do groszy w jednym miejscu (np. `roundTo2` w
utils) i stosować konsekwentnie.

### D3 (Niska) — `VITE_HOUSEHOLD_ID` w bundlu
Pliki: `src/services/api.js:6,80-91`, `.env.example:3`

Fallback `VITE_HOUSEHOLD_ID` jest wkompilowany do frontendu (prefiks `VITE_`).
Pod obecnym RLS jest nieaktywny (odczyty wymagają `auth.uid()`), ale to legacy,
które warto usunąć razem z S3, by uniknąć wrażenia „ukrytego" identyfikatora
gospodarstwa w kodzie klienta.

### Zweryfikowane jako OK
- Parsowanie kwot (`parseKwota`) poprawnie rozróżnia separator tysięcy/dziesiętny
  (`1.234,56 → 1234.56`), przepuszcza liczby bez re-parsowania.
- Walidacja dat (`normalizeDateToISO` + `isValidIsoDate`) odrzuca nieistniejące
  daty (30.02, 31.04) przez rekonstrukcję UTC.
- Import CSV utrzymuje wyrównanie `txMeta` do indeksów transakcji po filtrowaniu i
  usuwaniu wierszy (przebudowa kluczy).
- Kolejka offline: idempotentne ID operacji, `MAX_ATTEMPTS=3` z porzucaniem
  trwale błędnych wpisów, zachowanie nieudanych do ponowienia, ostateczny
  `clearQueue()` przy przepełnieniu quota — brak cichej utraty danych.
- Rozdział znaku kwoty w formatach bankowych (Obciążenia = wydatek ujemny,
  Uznania = przychód dodatni) jest spójny z `typ`.

## 3. Jakość kodu / architektura (obserwacje, nie błędy)

- **Podwójne pobieranie profilu**: każde wywołanie API robi `getHouseholdId()` →
  `getUserProfile()` = 2 round-tripy (`auth.getUser` + `select profiles`) na
  każdą operację. Warto scache'ować `household_id` w pamięci na czas sesji
  (memoizacja/kontekst) — redukcja opóźnień i obciążenia.
- **Mieszane ścieżki importu**: część komponentów w `/components` (poza `src`),
  część w `/src/components`; importy typu `'/components/...'` w `App.jsx`. Działa,
  ale utrudnia nawigację — warto skonsolidować do `src/`.
- **`console.error` bezpośrednio** w `CSVImport.jsx` i `Budgets.jsx` zamiast
  `logger` używanego w reszcie kodu — drobna niespójność.
- **Realtime + optimistic update**: po zapisie online `fetchData()` i subskrypcja
  realtime mogą odświeżyć listę podwójnie (bez błędu, lekki nadmiar zapytań).
